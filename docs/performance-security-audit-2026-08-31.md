# تدقيق التحمل والأمان والمزامنة — 2026-08-31

## النتائج المقاسة

نجح خادم API في الاستجابة إلى 300 طلب متوازٍ لنقطة `/api/health` عند تزامن 30 طلباً، ثم نجح في 1,000 طلب متوازٍ عند تزامن 100 طلب، وكانت كل النتائج HTTP 200. هذا اختبار صحة فقط؛ لا يمثل إنشاء طلب أو قبول رحلة أو كتابة GPS أو بث Realtime.

نجحت مجموعة الاختبارات الحالية: 25 ملف اختبار، 68 اختباراً ناجحاً واختبار واحد متجاوز. نجح فحص TypeScript وبناء خادم الإنتاج، ونجح `git diff --check`.

## حدود البنية الحالية

الخادم يستخدم Express وtRPC وSupabase عبر HTTP. مسار GPS يحقق التوكن والدور والنطاق الجغرافي، ثم يستدعي RPC محمية. قبول الطلب يعتمد على UPDATE ذري بشرط حالة الطلب وعدم وجود سائق. توجد فهارس أساسية للطلبات حسب العميل والسائق والحالة. لا يظهر في نقطة الدخول الحالية محدد معدل عام للطلبات، ولا مهلة صريحة لكل مسار، وحجم JSON المسموح به 50MB؛ وهذه نقاط تحتاج تشديداً قبل التوسع العام.

تتضمن دالة تحديث موقع السفير استعلامات إضافية للملف والطلب النشط ومؤشرات الرحلة، وقد ترسل إشعار Push عند الاقتراب. لذلك لا يجوز استنتاج سعة GPS من اختبار `/api/health` وحده.

## التقدير

لا يمكن إعطاء احتمال علمي مثل 2% أو 5% للتوقف أو الاختراق من دون مدة تشغيل وقياسات إنتاجية وسجلات مزود الاستضافة. التقدير الصحيح حالياً نوعي: توقف Metro أو المعاينة في التطوير ممكن وظهر في السجل كـ`Premature close`، لكنه لا يثبت توقف API الإنتاجي. توقف الخدمة السحابية أو قاعدة البيانات ممكن بسبب عطل مزود أو شبكة أو حصص أو صيانة. الضغط العالي قد يسبب طوابير وزمن استجابة مرتفعاً قبل الانهيار. الاختراق ممكن نظرياً، وتقل مخاطره مع RLS وJWT وعدم رفع الأسرار، لكنه لا يمكن ضمانه بصفر مطلق.

## توصيات قبل التوسع

إضافة rate limiting لكل IP وuser ولتحديث GPS، تحديد مهلات ودوائر إلغاء للطلبات الخارجية، خفض حد JSON العام، فصل طابور الإشعارات عن مسار GPS، إضافة مراقبة للزمن والأخطاء والاتصالات، واختبار حمل مصطنع على بيئة منفصلة لمسارات القراءة والكتابة مع بيانات تجريبية معزولة. كما ينبغي إعداد تنبيهات Supabase ونسخ احتياطية واختبار استعادة، وعدم اعتبار الخريطة أو مزود البلاطات مقياساً لسعة قاعدة البيانات.
